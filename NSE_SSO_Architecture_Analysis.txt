B. CURRENT NSE LOGIN FLOW (VERIFIED)
======================================

Endpoint  : POST /api/v1/auth/login  (also served at POST /auth/login)
File      : routers/auth.py lines 17-33
Function  : nse_login(payload: LoginRequest)

Sequence:
1. Client sends { "username": "...", "password": "..." }
2. routers/auth.py compares against settings.APP_USERNAME / settings.APP_PASSWORD
3. If mismatch -> HTTP 401 "Invalid username or password"
4. If match -> jose.jwt.encode({ "sub": username, "exp": now + JWT_EXPIRE_MINUTES }, JWT_SECRET, HS256)
5. Returns { status, message, access_token, token_type: "Bearer" }

CRITICAL FINDING:
There is exactly ONE hardcoded application-level account (APP_USERNAME / APP_PASSWORD from .env).
This is a single shared credential - not a per-user account system.
Every frontend user logs in with the same username/password.

Verification logic (auth/dependencies.py lines 8-15):

  require_auth(credentials: HTTPAuthorizationCredentials)
    -> jwt.decode(token, JWT_SECRET, algorithms=["HS256"])
    -> raises HTTP 401 on JWTError
    -> returns raw token string (not a user object)

The decoded payload is NEVER inspected after verification.
The sub claim is validated by signature only - no user lookup against a database occurs.
Any valid signed JWT grants full access to all protected routes.

CAN A BACKEND CREATE A SESSION WITHOUT A PASSWORD?
YES. Because there is no user table, no per-user identity, and no DB session,
any system that knows JWT_SECRET can mint a valid token.
This is the exact property needed for SSO.

F. NSE INVESTOR IDENTITY AND TRANSACTION MAPPING (VERIFIED)
=============================================================

Every NSE business API follows this pattern:

1. Frontend sends a request body containing client_code (and other investor fields)
2. FastAPI validates the JWT (confirms the caller is the trusted application)
3. FastAPI forwards the payload to NSE exchange using application-level credentials
   (NSE_LOGIN_USER_ID, NSE_API_SECRET, NSE_API_LICENSE_KEY, NSE_MEMBER_ID)
4. NSE exchange processes the transaction for the investor identified by client_code
5. FastAPI saves the result to its local PostgreSQL DB

NSE exchange authentication (auth/nse_auth.py) is completely separate from customer login:
- Uses PBKDF2-HMAC-SHA1 + AES-128-CBC encryption of "api_secret|random_number"
- Builds a Basic Authorization header with "login_user_id:encrypted_password"
- Adds memberId header
- Regenerated fresh on every request (random salt + IV each time)
- This is the member/broker credential, NOT the end-investor credential

G. AUTHENTICATION MIDDLEWARE (VERIFIED)
=========================================

File: auth/dependencies.py

  bearer_scheme = HTTPBearer()

  def require_auth(credentials: HTTPAuthorizationCredentials = Depends(bearer_scheme)):
      jwt.decode(credentials.credentials, settings.JWT_SECRET, algorithms=["HS256"])
      return credentials.credentials  # returns raw token string

Applied in main.py as a router-level dependency on all 34 business routers.
The auth router itself (/auth/login) is NOT protected.

What require_auth does NOT do:
- Does not extract or validate the sub claim
- Does not look up a user in a database
- Does not check user roles or permissions
- Does not check token revocation
- Does not distinguish between users - any valid token grants identical access

J. SSO COMPATIBILITY ASSESSMENT (VERIFIED + INFERRED)
=======================================================

The existing FastAPI architecture is HIGHLY COMPATIBLE with SSO. Here is why:

1. No per-user DB table exists
   There is nothing to conflict with. SSO does not need to replace a user system;
   it only needs to issue a valid JWT.

2. require_auth only checks JWT signature
   Any JWT signed with JWT_SECRET and not expired will pass. A new SSO endpoint
   can mint such a token without touching any existing code.

3. JWT_SECRET is already shared
   The same secret used by the login endpoint can be used by an SSO endpoint to
   mint tokens. No new secret infrastructure is needed.

4. No session storage
   There is no session table to maintain. Token validity is purely cryptographic.

5. The sub claim is never read after verification
   The SSO token can embed the Lendrix UUID in sub without breaking any existing route.

6. All business routes are stateless
   They accept client_code in the request body. After SSO, the frontend can supply
   the correct client_code for the authenticated user.

What is MISSING and must be added:
- A lendrix_user_nse_mapping table linking lendrix_uuid -> client_code
- A new POST /api/v1/auth/sso/callback endpoint
- A one-time authorization code store (Redis or PostgreSQL table with TTL)
- A new GET /api/v1/auth/me endpoint to return the mapped client_code for the current JWT


K. REQUIRED NODE.JS CHANGES
=============================

File to create/modify: New SSO controller in the Lendrix Express backend

1. New endpoint: POST /auth/sso/generate-code
   - Requires valid Lendrix JWT (existing require_auth middleware)
   - Generates a cryptographically random 32-byte hex code
   - Stores { code, lendrix_uuid, expires_at: now + 60s, used: false } in PostgreSQL or Redis
   - Returns { code } to the frontend (never in a URL)

2. New endpoint: POST /auth/sso/verify-code (server-to-server only)
   - Accepts { code, nse_server_secret } - a shared secret known only to Node.js and FastAPI
   - Validates code exists, not expired, not used
   - Marks code as used
   - Returns { lendrix_uuid, email, pan } to FastAPI

3. The nse_server_secret must be a strong random value stored in both .env files,
   never exposed to the browser.

N. SECURITY FINDINGS AND RISKS
================================

Only findings supported by actual source code are reported.

--- CRITICAL ---

N-1: Single shared application credential (VERIFIED)
  File   : config.py lines 14-15, routers/auth.py lines 18-19
  Detail : APP_USERNAME and APP_PASSWORD are a single shared credential for all users.
           Any person who knows these credentials has full access to all NSE investor
           operations for all clients. There is no per-user authorization.
  Risk   : A compromised credential gives an attacker unrestricted access to place
           orders, register mandates, and modify SIPs for any investor.

N-2: No ownership enforcement on client_code (VERIFIED)
  Files  : All routers (routers/order.py, routers/sip.py, etc.)
  Detail : Any authenticated caller can submit any client_code in a request body.
           There is no check that the authenticated user owns or is authorized to
           act on that client_code. A logged-in user could submit transactions for
           another investor's client_code.
  Risk   : Horizontal privilege escalation across all financial transaction endpoints.

N-3: /admin/change-api-secret has no role check (VERIFIED)
  File   : routers/misc_services.py line 68
  Detail : Any valid JWT holder can call POST /api/v1/admin/change-api-secret,
           which rotates the NSE API secret. This would break all NSE connectivity
           until the new secret is retrieved and stored.
  Risk   : Denial of service against all NSE operations.

--- HIGH ---

N-4: No token revocation or logout (VERIFIED)
  Files  : routers/auth.py, auth/dependencies.py
  Detail : There is no logout endpoint and no token blacklist. A stolen JWT remains
           valid until expiry (60 minutes by default).
  Risk   : Session hijacking with no remediation path.

N-5: No refresh token mechanism (VERIFIED)
  File   : config.py, routers/auth.py
  Detail : The 60-minute JWT has no refresh path. Users must re-authenticate after
           expiry. In an SSO context, this means the user would be silently logged
           out of the NSE app while still logged into Lendrix.

N-6: Duplicate unprotected login path (VERIFIED)
  File   : main.py lines 71-72
  Detail : The auth router is registered twice: once at /api/v1 and once at /
           (no prefix). This means /auth/login and /api/v1/auth/login both work.
           The unversioned path was added for "frontend compatibility" but creates
           an undocumented surface.

--- MEDIUM ---

N-7: CORS wildcard fallback (VERIFIED)
  File   : main.py lines 55-62
  Detail : If ALLOWED_ORIGINS is empty in .env, the CORS policy falls back to a
           hardcoded list including http://localhost:3000, http://localhost:5173,
           http://localhost:8080. In production, if the env var is accidentally
           unset, local development origins would be allowed.

N-8: require_auth returns raw token, not decoded payload (VERIFIED)
  File   : auth/dependencies.py line 15
  Detail : The dependency returns credentials.credentials (the raw JWT string)
           rather than the decoded payload. This means every route that needs user
           identity would have to decode the token again, or the identity is simply
           not used. Currently no route uses the returned value for authorization
           decisions.

N-9: No rate limiting on login endpoint (VERIFIED)
  File   : routers/auth.py
  Detail : The login endpoint has no rate limiting, no account lockout, and no
           brute-force protection.

--- LOW ---

N-10: server.log committed to repository (VERIFIED)
  File   : server.log in repository root
  Detail : Log files should not be committed. They may contain IP addresses,
           request paths, or timing information.

N-11: passlib[bcrypt] in requirements but never used (VERIFIED)
  File   : requirements.txt
  Detail : passlib[bcrypt]==1.7.4 is listed as a dependency but there is no
           password hashing anywhere in the codebase (no user table, no password
           storage). This is dead dependency weight and may indicate an earlier
           design that was abandoned.
